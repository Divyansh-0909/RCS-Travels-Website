  WHAT IS ACTUALLY WRONG, ordered by how much it costs:

  1. THE 12-HOUR WINDOW IS THE SINGLE BIGGEST WASTE. A ride booked 12 h ahead enters
     the candidate set immediately and gets a FULL getDriver sweep (20->80 km rings,
     one sequential FCM per candidate) every 5 minutes until it is assigned — about
     144 complete sweeps for one ride, nearly all of them pointless because no
     driver commits to a pickup half a day out. PHASE 2 below already specifies the
     right window: scheduledAt <= now + 60 min, and 3 h ahead for outstation. The
     code never matched its own spec. Fixing only this cuts the work ~12x and is
     a one-line change. Do this first.

  2. getDriver NOTIFIES DRIVERS ONE AT A TIME AND WAITS FOR EACH. With a 30 s accept
     window and 10 candidates that is 5 minutes to fill a single booking. Real
     ride-hailing broadcasts to the nearest K drivers simultaneously and takes the
     first accept. That is the structural fix; the "30s -> 20s" item already on this
     list only shrinks the constant, it does not change the shape.

  3. setInterval WITH AN ASYNC CALLBACK OVERLAPS ITSELF. It does not wait for the
     previous run to finish, and a tick can easily exceed 5 min (see #2). Two runs
     then sweep the same booking concurrently and double-notify the same drivers.
     claimBooking (added with the async-assignment work) keeps the DB coherent, but
     the duplicate FCM is real and a driver sees the same ride twice. Fix: a
     self-scheduling setTimeout that queues the next tick only when the previous one
     finishes — the exact shape TrackingPage's status poll already uses.

  4. NO ATTEMPT TRACKING, SO NO BACKOFF AND NO ALERT LIMIT. Every tick retries every
     eligible booking identically, and getDriver's `triedDriverIds` set is per-call,
     so the same unreachable drivers get pinged again next tick. Worse, the "no
     driver found" admin WhatsApp fires EVERY 5 MIN in the final hour — 12 messages
     for one failing booking. Add to Booking: lastAssignmentAttemptAt,
     assignmentAttempts, adminAlertedAt. Then skip anything attempted in the last
     N minutes, alert the admin once, and the sweep becomes idempotent across
     restarts instead of restarting its memory every time Render wakes.

  5. IT ONLY RUNS WHILE RENDER IS AWAKE. Free tier sleeps; the keep-alive cron
     mitigates that but does not guarantee it. A 06:00 pickup can be missed
     entirely if nothing pinged the service overnight.

  ORDER: 1 (one line, biggest win) -> 3 (correctness) -> 4 (schema + backoff)
  -> 2 (restructures getDriver) -> 5.

  LATER, NOT NOW: polling is a stand-in for a scheduler. The real design enqueues a
  job at (scheduledAt - leadTime) when the booking is created, so nothing scans for
  work at all. Supabase ships pg_cron and pg_net, so this is reachable without new
  infrastructure — but it is not worth the complexity until volume justifies it,
  and items 1-4 remove most of the pain for a fraction of the effort. Do NOT start
  here.

X PHASE 2 — Core Backend APIs (Day 2-4)
---------------------------------------
Goal: Build only what the booking flow needs.

  AUTH ENDPOINTS (build first — everything else depends on auth):
  POST  /api/auth/send-otp                ← generate OTP, store with 5-min expiry, send via WhatsApp
  POST  /api/auth/verify-otp              ← verify OTP → find/create Clerk user by fake email
                                            → return Clerk sign-in ticket to frontend
  Note: Fake email format: 91{phone}@rcs-travels.com
        OTP stored in otp_verifications table (phone, otp_hash, expires_at, used)
        On verify: create Clerk user via Admin SDK if not exists, return signInToken
        Frontend completes sign-in via: signIn.create({ strategy: "ticket", ticket })

  POST  /api/fare/estimate                ← fare calc (fixed table OR Google Routes API)
  POST  /api/bookings                     ← create booking (scheduled or on-spot)
  GET   /api/bookings/:id/status          ← polling endpoint for customer tracking page
  PATCH /api/driver/rides/:id/accept      ← driver accepts the ride
  PATCH /api/driver/rides/:id/decline     ← driver declines, system tries next driver
  GET   /api/admin/bookings               ← list all bookings for admin visibility

Booking Modes:

  Scheduled (primary — up to 7 days in advance):
    - scheduledAt is set and at least 30 minutes from now (enforced in POST /api/bookings)
    - If scheduledAt is set but less than 30 minutes away → reject with HTTP 422
    - Booking created immediately with status = confirmed (fare locked, code issued)
    - Driver is NOT assigned at booking time
    - Background job (assignScheduledRides.js) runs every 5 minutes
      → assigns drivers to bookings where status = confirmed AND scheduledAt <= now + 60 min
      → for outstation rides: trigger 3 hours before scheduledAt
    - Status flow: confirmed → assigned → en_route → reached → started → completed

  On-Spot (secondary — subject to availability):
    - scheduledAt is null (no time given, ride wanted now)
    - REVISED: assignment no longer runs inside the request. POST /api/bookings creates
      the row as `pending`, fires startAssignment(bookingId) detached, and responds
      immediately with { status: 'pending' }. The client then shows the "Requesting a
      ride" panel and polls GET /api/bookings/:id/status every 5s.
      WHY: getDriver walks 20→80 km rings with a sequential FCM call per candidate. It
      can run for minutes. Awaiting it inside the request meant the searching panel was
      UNREACHABLE — the user just watched the Confirm button say "Booking..." until a
      driver was found or the whole search gave up.
    - If no driver is reached → status becomes `no_driver` (NOT deleted, NOT a 503).
      `no_driver` is deliberately absent from ACTIVE_STATUSES, which is what lets the
      rider retry immediately — that's the job the old delete-on-failure was doing.
      Side effect: failed bookings now persist in ride history. That's intended (the
      rider can see it, and you can measure the failure rate).
    - Status flow: pending → assigned → en_route → reached → started → completed
                   pending → no_driver (terminal)
    - Crash guard: GET /:id/status lazily expires any `pending` row older than
      ASSIGNMENT_DEADLINE_MS (5 min). No scheduler needed — the only thing waiting on the
      answer is the poll that just arrived. Covers a Render restart mid-search, which
      would otherwise strand the booking and make the client poll forever.
    - Race, and how it's closed: the lazy expiry and a still-running getDriver could both
      write. getDriver now claims the booking with a guarded updateMany
      (status IN pending|confirmed) BEFORE decrementing driver capacity, and abandons the
      search if the claim fails. Claim-before-capacity matters — the old order took the
      seat first, so guarding the booking write alone would leak a seat on every lost
      claim. It also re-checks the status between radius rings so an expired booking
      stops pinging drivers. `confirmed` must stay in the claimable set: the scheduled
      job (assignScheduledRides.js) calls the same getDriver on confirmed bookings.
      STILL OPEN: a driver can receive one FCM for a booking that expires during that
      exact send — sendFCM returning true means DELIVERED, not accepted. Real fix is a
      two-phase notify → accept → claim, which is a driver-app change (Phase 5).

Auto-Assignment Flow (shared logic, used by both modes):
  1. Query nearest online + active driver (verificationStatus = approved) using Haversine distance
     from driver_locations table
  2. Send FCM push notification to that driver (stub in Phase 2, real in Phase 6)
  3. Store assignment attempt timestamp on the booking
  4. Driver accepts  → status becomes assigned, customer sees driver info
  5. Driver declines or 30s passes → try next nearest driver
  6. No drivers available:
       On-spot    → booking status becomes no_driver (terminal); the client's poll
                    surfaces the "No drivers nearby" panel
       Scheduled  → booking stays confirmed, admin alerted via WhatsApp

   !! MODEL CHANGED (28 Jul 2026, Raju's direction) — the deposit is no longer

     - POSTER sets the deposit amount himself when he posts the ride (his own

       time, since no rational claimer would ever accept the reverse).
     - CLAIMER pays that deposit by UPI to claim it.

     - MINIMUM DEPOSIT = ₹100 (Raju's number — supersedes Claude's earlier
