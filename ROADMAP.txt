- !! A CAPTAIN CAN BOOK A RIDE AND THEN DRIVE IT HIMSELF. Nothing anywhere stops
  him. Found 14 Aug 2026 while working out how to test the driver flow end to end
  on one phone — which is the same thing, done on purpose.
  HOW IT WORKS, and why it is not an accident of the data model: the Clerk identity
  is derived from the phone number alone (routes/hybridAuth.js), so one person with
  one number is one Clerk user holding a User row AND a Driver row. That is
  deliberate and correct — a captain who also books cabs is one person. What is
  missing is anybody checking the two apart at dispatch: candidatesWithin filters on
  radius, freshness, is_online, is_active, suspension, approval and vehicle class,
  and never once asks who booked the ride. Neither accept endpoint asks either.
  Both rows already carry clerkId, so the join is sitting right there unused.
  WHY IT IS HARMLESS TODAY, and exactly when it stops being: fares are fixed by
  destination and commission moves money between two accounts belonging to the same
  man, so a self-booked ride nets out to roughly nothing. It becomes a live fraud
  vector the moment anything is payable ON a ride rather than FOR one — the ride
  acceptance deposit (block 10), the driver wallet, or any completion-count or
  streak incentive. All three are already on this roadmap. Whoever builds the first
  of them owns this.
  IT IS ALSO A QUEUE EXPLOIT RIGHT NOW, at zero cost: lastOfferedAt is stamped when
  an offer goes OUT (markOffered, deliberately, see the comment there), so booking a
  ride to yourself and ignoring it spends a rival's turn and moves you up the
  fairness ordering. Small at this fleet size, not nothing.
  THE FIX: driver.clerkId !== booking.user.clerkId, in candidatesWithin and in both
  PATCH .../accept handlers — the query is the one that matters, the endpoints are
  the ones that close the race. Cheap, and it needs a test.
  DO NOT LAND IT WITHOUT AN ESCAPE HATCH. Self-booking is currently the only way to
  drive the whole flow — book, dispatch, offer, accept, en_route, arrive, OTP,
  complete — on one handset with one number, and there is no second test phone. An
  env flag (ALLOW_SELF_ASSIGN=1, dev only, off by default like FCM_ALWAYS_ACCEPT is
  meant to be) keeps that possible. Guard it the way that flag should have been:
  refuse to honour it when NODE_ENV is production.

- Women get a safer road route for rides.
  WHY: uni is in a remote area; the shortest route passes through shady areas that
  girls avoid. A slightly longer highway route is safer. Goal: female users (or anyone
  who opts in) are routed via the highway automatically.

  KEY INSIGHT: Google Routes API has NO concept of a "shady"/"safe" route. That
  knowledge is local — but it does NOT follow that we should name the road ourselves.

  SUPERSEDED (29 Jul 2026): the original plan forced every campus trip through ONE
  hardcoded highway waypoint. That can only ever be right for a single corridor —
  the shortcut riders avoid is on the way to some destinations and nowhere near the
  others, so the same waypoint that fixes a Noida run detours a Dadri one. The
  constant was never filled in, which is the only reason it never shipped wrong.

  BUILT INSTEAD — mark the ground, not the road:
    - backend/data/shady-zones.geojson holds POLYGONS around the avoided stretches.
      SEPARATE from zones.geojson on purpose (fare zones are drawn around
      destinations; these are drawn around roads). EMPTY would mean the feature is
      fully dormant: no alternatives requested, no toggle shown, nothing charged.
      [NO LONGER EMPTY] The corridor is drawn and the feature is live. Redrawn 13 Aug
      2026 — the Dadri-Bisrakh zone was removed and the Greater Noida east corridor
      reshaped to cover the Dadri Main Rd / GN West Link Rd alternative, which had been
      testing clean. Every alternative on campus <-> Greater Noida now scores shady,
      which is what makes the campus gates fire. Zone `fallback` is still null on the
      remaining zone; the gates cover campus trips instead.
    - The estimate asks Routes for `computeAlternativeRoutes`, decodes each one and
      measures how far it runs inside a shady polygon (sampled every 50 m, so a
      sparse motorway polyline can't slip through; 400 m inside is the threshold,
      so clipping a corner doesn't count). Primary clean -> nothing offered.
      Primary shady -> fastest clean alternative wins. Google finds the Eastern
      Peripheral on its own; no highway is named anywhere in the code.
    - Only if EVERY alternative is shady does it force a waypoint, and it re-verifies
      the result is clean before offering it. Two sources, in this order:
        CAMPUS GATES (safeRoute.js) — a trip with either end inside the campus radius
          uses a fixed point that puts it on the Eastern Peripheral. DIRECTIONAL: two
          points 642 m apart, outbound 28.520718,77.600243 and inbound 28.518866,
          77.594022, because the carriageways are separate. Measured 13 Aug 2026:
          forcing an OUTBOUND trip through the inbound gate returns 42.25 km / 60 min
          and STILL crosses the zone, vs 27.57 km / 39 min clean through the right one.
        ZONE `fallback` — the per-zone property, for trips with neither end on campus.
          Still null on every zone, so this half remains dead; the gates cover the
          campus traffic the feature was actually built for.
      GATED ON primaryShady, NOT on "no clean alternative was found". classifyRoutes
      returns safe:null for BOTH "the default road is already fine" and "nothing clean
      was offered", so a caller keying off !safe forces a detour on trips whose road
      never touched a zone. That shipped briefly and turned the 4.6 km campus->Dadri
      run into 11.8 km with ₹150 on it. tests/safeRoute.test.js guards the distinction.
    - AN ENDPOINT INSIDE A ZONE is not offered a detour at all: every route to it must
      finish inside, so there is nothing to route around. Checked before any call.
    - The chosen route is reduced back to ONE coordinate (the point furthest from
      the primary path — a midpoint sits on shared road and forces nothing) and
      stored on the booking as safeWaypointLat/Lng, because a Maps nav link takes
      coordinates, not "Google's second suggestion".
    - backend/scripts/check-shady-zones.js routes campus -> every fare zone and
      reports which destinations actually cross the polygon and whether a clean
      alternative exists. RUN IT after drawing a zone — it is the difference
      between knowing this works and hoping.

  ORIGINAL ANALYSIS (pre-13 Aug), ordered by how much it costs:

  1. THE 12-HOUR WINDOW IS THE SINGLE BIGGEST WASTE. A ride booked 12 h ahead enters
     the candidate set immediately and gets a FULL getDriver sweep (20->80 km rings,
     one sequential FCM per candidate) every 5 minutes until it is assigned — about
     144 complete sweeps for one ride, nearly all of them pointless because no
     driver commits to a pickup half a day out. PHASE 2 below already specifies the
     right window: scheduledAt <= now + 60 min, and 3 h ahead for outstation. The
     code never matched its own spec. Fixing only this cuts the work ~12x and is
     a one-line change. Do this first.

  2. getDriver NOTIFIES DRIVERS ONE AT A TIME AND WAITS FOR EACH. With a 30 s accept
     window and 10 candidates that is 5 minutes to fill a single booking. Real
     ride-hailing broadcasts to the nearest K drivers simultaneously and takes the
     first accept. That is the structural fix; the "30s -> 20s" item already on this
     list only shrinks the constant, it does not change the shape.

  3. setInterval WITH AN ASYNC CALLBACK OVERLAPS ITSELF. It does not wait for the
     previous run to finish, and a tick can easily exceed 5 min (see #2). Two runs
     then sweep the same booking concurrently and double-notify the same drivers.
     claimBooking (added with the async-assignment work) keeps the DB coherent, but
     the duplicate FCM is real and a driver sees the same ride twice. Fix: a
     self-scheduling setTimeout that queues the next tick only when the previous one
     finishes — the exact shape TrackingPage's status poll already uses.

  4. NO ATTEMPT TRACKING, SO NO BACKOFF AND NO ALERT LIMIT. Every tick retries every
     eligible booking identically, and getDriver's `triedDriverIds` set is per-call,
     so the same unreachable drivers get pinged again next tick. Worse, the "no
     driver found" admin WhatsApp fires EVERY 5 MIN in the final hour — 12 messages
     for one failing booking. Add to Booking: lastAssignmentAttemptAt,
     assignmentAttempts, adminAlertedAt. Then skip anything attempted in the last
     N minutes, alert the admin once, and the sweep becomes idempotent across
     restarts instead of restarting its memory every time Render wakes.

  5. IT ONLY RUNS WHILE RENDER IS AWAKE. Free tier sleeps; the keep-alive cron
     mitigates that but does not guarantee it. A 06:00 pickup can be missed
     entirely if nothing pinged the service overnight.

  ORDER: 1 (one line, biggest win) -> 3 (correctness) -> 4 (schema + backoff)
  -> 2 (restructures getDriver) -> 5.

     them. Recorded 14 Aug 2026 after researching how Uber, Ola and Rapido do this,
     because the answer for them is not the answer for us and the gap is the point.
     Their published designs (MQTT/gRPC ingestion, Kafka, Redis GEO or H3 in RAM,
     Postgres kept off the hot path entirely) are correct at five million drivers
     and 1.25M writes/second. WE ARE AT ROUGHLY 1.7 WRITES/SECOND — fifty captains,

     adaptive cadence is what buys that: a flat 4-second ping for the same fleet

     1. OEM BATTERY MANAGERS — the one unsolved risk in background location, and

        managers that kill background apps EVEN WITH A VALID FOREGROUND SERVICE,
        and between them that is most of the handsets our captains actually own.
        It is the top source of "why did I stop getting rides" for every Indian
        driver app, which is why Ola and Rapido both walk drivers through
        disabling battery optimisation and whitelisting autostart during
        onboarding. NEEDS AN ONBOARDING SCREEN with per-OEM steps
        (dontkillmyapp.com documents them), not just a permission prompt.
        The staleness filter is the backstop when it happens anyway: he drops out
        of dispatch instead of sitting on the map frozen and unreachable.
        Also note none of the background path runs in Expo Go — testing it needs a
        dev build on a real handset.

        without calling the driver context's refresh() and the whole drive to
        pickup runs at the 20-second idle cadence while a rider watches.

        driver IS and never where he WENT, so a "he took the long way" dispute has
        nothing behind it. Buffer the path in memory during a ride, bulk INSERT on
        completion. INSERT-only, so none of the update-churn concern applies.
        NOTE THE FARES ARE FIXED BY DESTINATION, so unlike a metered operator this

        is why it sits below background location rather than above it.

        wrong place for this at volume: every UPDATE writes a dead tuple, and geog

        non-issue today is that driver_locations is ONE ROW PER DRIVER — a ~50-row

          SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
            FROM pg_stat_user_tables WHERE relname = 'driver_locations';

        near zero, or when sustained writes pass a few hundred per second. At that
        point Redis GEO holds live position and Postgres keeps history only.

  PATCH /api/driver/rides/:id/decline     ← driver declines, system tries next driver
  GET   /api/admin/bookings               ← list all bookings for admin visibility

Booking Modes:

  Scheduled (primary — up to 7 days in advance):
    - scheduledAt is set and at least 30 minutes from now (enforced in POST /api/bookings)
    - If scheduledAt is set but less than 30 minutes away → reject with HTTP 422
    - Booking created immediately with status = confirmed (fare locked, code issued)
    - Driver is NOT assigned at booking time
    - Background job (assignScheduledRides.js) runs every 5 minutes
      → assigns drivers to bookings where status = confirmed AND scheduledAt <= now + 60 min
      → for outstation rides: trigger 3 hours before scheduledAt
    - Status flow: confirmed → assigned → en_route → reached → started → completed

  On-Spot (secondary — subject to availability):
    - scheduledAt is null (no time given, ride wanted now)
    - REVISED: assignment no longer runs inside the request. POST /api/bookings creates
      the row as `pending`, fires startAssignment(bookingId) detached, and responds
      immediately with { status: 'pending' }. The client then shows the "Requesting a
      ride" panel and polls GET /api/bookings/:id/status every 5s.
      WHY: getDriver walks 20→80 km rings with a sequential FCM call per candidate. It
      can run for minutes. Awaiting it inside the request meant the searching panel was
      UNREACHABLE — the user just watched the Confirm button say "Booking..." until a
      driver was found or the whole search gave up.
    - If no driver is reached → status becomes `no_driver` (NOT deleted, NOT a 503).
      `no_driver` is deliberately absent from ACTIVE_STATUSES, which is what lets the
      rider retry immediately — that's the job the old delete-on-failure was doing.
      Side effect: failed bookings now persist in ride history. That's intended (the
      rider can see it, and you can measure the failure rate).
    - Status flow: pending → assigned → en_route → reached → started → completed
                   pending → no_driver (terminal)
    - Crash guard: GET /:id/status lazily expires any `pending` row older than
      ASSIGNMENT_DEADLINE_MS (5 min). No scheduler needed — the only thing waiting on the
      answer is the poll that just arrived. Covers a Render restart mid-search, which
      would otherwise strand the booking and make the client poll forever.
    - Race, and how it's closed: the lazy expiry and a still-running getDriver could both
      write. getDriver now claims the booking with a guarded updateMany
      (status IN pending|confirmed) BEFORE decrementing driver capacity, and abandons the
      search if the claim fails. Claim-before-capacity matters — the old order took the
      seat first, so guarding the booking write alone would leak a seat on every lost
      claim. It also re-checks the status between radius rings so an expired booking
      stops pinging drivers. `confirmed` must stay in the claimable set: the scheduled
      job (assignScheduledRides.js) calls the same getDriver on confirmed bookings.
      STILL OPEN: a driver can receive one FCM for a booking that expires during that
      exact send — sendFCM returning true means DELIVERED, not accepted. Real fix is a
      two-phase notify → accept → claim, which is a driver-app change (Phase 5).

Auto-Assignment Flow (shared logic, used by both modes):
  1. Query nearest online + active driver (verificationStatus = approved) using Haversine distance
     from driver_locations table
  2. Send FCM push notification to that driver (stub in Phase 2, real in Phase 6)
  3. Store assignment attempt timestamp on the booking
  4. Driver accepts  → status becomes assigned, customer sees driver info
  5. Driver declines or 30s passes → try next nearest driver
  6. No drivers available:
       On-spot    → booking status becomes no_driver (terminal); the client's poll
                    surfaces the "No drivers nearby" panel
       Scheduled  → booking stays confirmed, admin alerted via WhatsApp

   settle it against wallet balance, so no payment step sits in the hot path.

   accounts-payable ledger: the PLATFORM credits it (coupon reimbursement,
   deposit refunds), the DRIVER spends it (fees) or withdraws it. The moment a
   driver can TOP IT UP with his own UPI to hold a balance, it becomes a
   prepaid payment instrument under RBI PPI rules and inherits exactly the
   licensing exposure block 7 was designed to avoid. NO TOP-UP. Credit in,
   spend or withdraw out.

   An outside design proposed funding the wallet by Razorpay top-up; when the
   PPI line above was pointed out, it proposed instead DELETING the wallet and
   replacing it with a per-ride PAYMENT AUTHORISATION against the driver's own
   payment method. BOTH REJECTED, for different reasons:
     - TOP-UP crosses the regulatory line above. Unchanged, not reopened.
     - PER-RIDE AUTHORISATION puts a gateway round-trip back inside accept —
       the exact failure ACCEPT-FLOW LATENCY above already predicted. It is
       also a card pre-auth concept; on UPI it means a one-time mandate, a
       heavier product with its own onboarding, for drivers who are on UPI.
   THE LEDGER DEBIT IS NOW THE PRIMARY DESIGN, not the "cheap mitigation if it
   bites" this block called it on 8 Aug. Accept writes a `deposit_hold` of
   −(pct × fare); completion writes `deposit_refund` of the same amount back.
   No gateway anywhere in the hot path.
   WHY THE WALLET SURVIVES THE PPI ARGUMENT AND THE AUTHORISATION MODEL DOES
   NOT: the test is WHO FUNDED THE BALANCE, not whether a balance exists. A
   balance only the platform can credit, which the driver spends on fees or
   withdraws, is ACCOUNTS PAYABLE — money owed to him. That is being a debtor,
   not issuing a payment instrument. Deleting it would also turn every
   ₹100-₹500 coupon reimbursement (block 12) into a separate RazorpayX bank
   transfer with a real per-transaction fee, fired once per redeemed ride.
   Accrue in the ledger, settle periodically.
   AVAILABLE / HELD / TOTAL IS A UI DERIVATION OVER THE LEDGER, NOT NEW
   COLUMNS. Total = sum(entries) = Driver.walletBalance. Held = the sum of
   `deposit_hold` entries whose booking has no matching `deposit_refund`.
   Available = total − held. Nothing extra is stored, and the captain still
   sees "₹80 held for booking X, returned when the ride completes".
   TERMINOLOGY IS PART OF THE SPEC, not UI polish. Say "₹80 HELD from wallet"
   on accept and "hold RELEASED" on completion — never "paid". "Paid" is
   reserved for money that genuinely leaves him: a fine, a marketplace
   deposit. A driver who reads "paid ₹80" on every accept concludes he is
   being charged per ride, and he is not.

   earnings to accrue. He may pay by Razorpay to clear it, CAPPED AT THE DEBT

   spendable balance. That is settling a receivable, not loading an

11. OVERCHARGE FLAG -> STRIKES -> FINE -> SUSPENSION
   SCHEMA DONE AND MIGRATED 8 Aug 2026. NO CODE WRITES IT YET.
   OverchargeFlag is UNIQUE ON bookingId — one ride, one flag. Without that a
   single annoyed rider taps five times and suspends a driver off one trip, which
   is the cheapest possible abuse of the whole system. It snapshots `fareAtFlag`
   because Booking.fare can still move (changed drop, added stop) and the flag
   has to be reviewable against the number the rider actually saw.
   Driver.suspendedAt + suspensionReason are separate from isActive, as specified,
   and driverAssignment.js now filters `suspendedAt: null`.
   THRESHOLD CHANGED 8 Aug: the message sent to Raju says 3 complaints -> fine
   (not "more than 3"), 5 -> suspend. That also closes the strike-3 gap flagged
   below. Nothing enforces either number yet — the fine amount is still his.
   The rider gets a "Driver overcharged" button on a completed ride. Pressing
   it FLAGS the driver.
     - more than 3 flags  ->  the driver is FINED
     - 5 flags            ->  the account is SUSPENDED, and ONLY AN ADMIN can
                              lift the suspension
   FINE AMOUNT STILL OPEN (Raju's number).
   SUSPENDED DRIVERS (his spec, block 9's source file): cannot go online,
   cannot receive ride-now, cannot receive scheduled offers, and LOSE ALL
   PENDING SCHEDULED OFFERS — those bookings immediately restart assignment.
   His full suspension grounds are wider than this feature: asking extra
   money, fraud, unsafe driving, misbehaviour, fake trips.
   [DONE] Suspension has its own columns — suspendedAt + suspensionReason — rather
   than reusing isActive, so "suspended for overcharging" is distinguishable from
   "deactivated" and the reason survives. requireApprovedDriver refuses a suspended
   captain WITH that reason.
   [DONE 13 Aug 2026] The admin mutation now exists — PATCH
   /api/admin/drivers/:id/suspension, a reason required to suspend and shown to
   him, idempotent by omission rather than by erroring (two admins on the same
   screen want the current state, not a 409). It deliberately does NOT touch
   verificationStatus: a suspended captain's paperwork is still in order, and
   suspension is a judgement about conduct, derivable from nothing.
   His pending scheduled offers are withdrawn with the suspension as of the same
   day, and those bookings go back into the pool — see block 9 for why that needed
   a change to the escalation rule as well.
   WHAT IS STILL MISSING is everything that would make this AUTOMATIC — the
   rider's "Driver overcharged" button, the flag rows, the counting, and the fine.
   Today a human decides and a human clicks.
   !! FINES LAND IN THE WALLET, and this is the elegant part: debit the fine
   from wallet credit; if the balance is short it goes NEGATIVE, and a
   negative balance blocks going online until it is cleared. No gateway, no
   collections, no chasing — and the coupon reimbursements he is owed pay it
   down automatically.
   TRADE-OFFS PUT TO THE USER AND KNOWINGLY ACCEPTED — these are recorded so
   they are not re-argued, and so the symptoms are recognisable if they show:
     - RAW FLAGS, NOT UPHELD ONES. A free rider-side button where 5 presses
       end a driver's income can be abused, and the honest false positive is
       common: a rider charged the 35% cancellation fee genuinely believes he
       was overcharged. Recommended and NOT adopted: admin review between flag
       and strike, and deduping repeat flags from the same rider.
     - NO DECAY WINDOW. 5 flags across two years counts the same as 5 in a
       week. Recommended and not adopted: a rolling 90-day window.
     - STRIKE 3 IS UNDEFINED by the rule as written ("more than 3" fines at 4,
       suspension at 5).
     - FLAG IS A BOOLEAN, not an amount. Capturing "asked for ₹200 extra"
       would make an admin review take five seconds against the stored fare /
       rideFare, and let a fine scale to the offence. Worth revisiting if
       reviewing flags turns out to be slow.
   If any of these turn into real problems in practice, THAT is the trigger to
   revisit — not a hunch beforehand.

12. CUSTOMER COUPONS + DRIVER RATINGS
   SCHEMA DONE AND MIGRATED 8 Aug 2026. NO CODE WRITES IT YET.
   DriverReview: unique on bookingId (a ride is rated once — a driver cannot
   collect five ratings from one journey), rating 1-5 enforced in the route since
   Prisma has no check constraint. Average / total / recent are DERIVED from the
   table, NOT cached on Driver: nothing indexes a rating, the profile is not a hot
   path, and an average that drifts is worse than a sum.
   Coupon: a ROW per issued coupon, not a counter on User — the coupon outlives
   the month that earned it, and redemption has to be atomic. `@@unique([userId,
   earnedFor])` stops one month issuing two coupons however many times the job
   runs; the unique `bookingId` stops the same coupon being spent on two
   bookings racing each other.
   !! THE EARNING RULE CHANGED 14 Aug 2026 — SPEND TIERS, NOT A RIDE COUNT.
   It was "₹100 after 6 completed rides in the same month". It is now:
     ₹2,000 in a calendar month  ->  ₹100
     ₹2,500                      ->  ₹200
     ₹5,000                      ->  ₹500
   HIGHEST THRESHOLD REACHED WINS, and ONE COUPON PER CUSTOMER PER CALENDAR
   MONTH — which `@@unique([userId, earnedFor])` already enforces, so the
   schema needs no change for this. Only `amount` now varies where it used to
   be the ₹100 default. COMPLETED RIDES ONLY; cancelled rides never count.
   ISSUE AT MONTH END, NOT CONTINUOUSLY (recommended 14 Aug, NOT YET CONFIRMED
   BY THE USER). This is the whole reason to prefer month-end: issue the
   moment a rider crosses ₹2,100 and they can redeem the ₹100 immediately,
   then climb to ₹5,200 — at which point the unique key blocks a second row
   and the first row cannot be upgraded because it is already redeemed. The
   rider earned ₹500 and received ₹100. Issuing once on the 1st is a single
   insert at the correct tier, with no upgrade path to get wrong and nothing
   to exploit. Show LIVE PROGRESS in-app during the month ("₹2,100 so far —
   ₹400 more for ₹200"), derived from bookings, never from a Coupon row.
   COUNT `rideFare`, NOT `fare` (recommended, NOT YET CONFIRMED). rideFareOf()
   already strips toll, carrier and airport fee. A rider should not earn
   coupon credit on money that went to NHAI — the same reason commission is
   charged on rideFare (services/commission.js).
   COUNT POST-COUPON VALUE (recommended, NOT YET CONFIRMED) — what the rider
   actually paid, or coupons compound into coupons.
   Customer pays fare − coupon in cash (₹400 fare, ₹100 coupon, ₹300
   collected). The DRIVER WALLET IS CREDITED 100% OF THE COUPON VALUE
   IMMEDIATELY on use — the driver is never out of pocket for the discount.
   This is the reason the wallet has to exist at all, independent of block 10,
   and the tier change makes it more so: the per-redemption credit is now up
   to ₹500.
   STILL TO DO: the month-end tiered issuing job, redemption inside the SIGNED
   FARE QUOTE (see the !! below — this is the trap), the wallet credit on
   redemption, and the review endpoints.
   STILL OPEN (asked 14 Aug, unanswered): (a) does commission's ₹800 floor
   test the fare BEFORE or AFTER the coupon? Tiers make this sharp — a ₹1,200
   ride with a ₹500 coupon lands at ₹700, under the floor, so the platform
   pays ₹500 AND forgoes ₹60 while the driver receives the full ₹1,200 either
   way (₹700 cash + ₹500 credit). Testing pre-coupon rideFare leaves the
   driver identical and costs ₹60 less each time. (b) Does a coupon EXPIRE?
   There is no `expiresAt` on the model and this block says "usable on any
   future ride". Unbounded ₹100 liabilities were tolerable; unbounded ₹500
   ones accumulate. A 3-month expiry is a small migration and is much easier
   before any coupons exist than after.
   !! THE SCHEMA COMMENT ABOVE `model Coupon` STILL DESCRIBES THE OLD 6-RIDE
   RULE, as does its note on `earnedFor`. Fix it when the issuing job is
   written — right now schema.prisma and this block disagree.
   !! COUPONS ARE MONEY-BEARING, SO THE COUPON MUST GO INSIDE THE SIGNED FARE
   QUOTE (see SERVER-SIDE FARE RECOMPUTATION below, which already says every
   new money-bearing field must). A coupon applied beside the quote instead of
   inside it is a discount anyone can forge in the request body. This is the
   trap in this feature.
   DRIVER'S RIDE CARD must break the money out in full: ride fare / coupon
   applied / customer pays / wallet credit. His principle, verbatim: every
   financial transaction is visible to the driver.
   RATINGS: 1-5 plus written review after every completed ride. Driver profile
   shows average rating, total reviews, completed rides, recent reviews.
