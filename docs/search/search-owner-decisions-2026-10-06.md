Missing/ambiguous/conflicting/ungrounded values become `resolutionRequirements`. They are field/control requirements, not AI questions. Missing values and advisory unsupported preferences do not cause additional model turns. Existing `followups` names are compatibility aliases for form requirements; no automatic conversation executor or conversational endpoint exists.

The deterministic `formResolution` projection distinguishes NEEDS_USER_RESOLUTION, READY_FOR_REVIEW and READY_FOR_SUBMISSION. It requires grounded pickup/drop, valid timing, actual vehicle selection, resolved conflicts, supported journey semantics, recomputed fare/route, location review and explicit final review. Edits invalidate derived confirmations and fare state. Parser/model output cannot set confirmations or call booking creation. This is a backend/UI contract; the customer NL UI remains off and no existing checkout path was replaced.

Advisory passenger counts remain visible without capacity-enforcement promises. Straightforward soft “AC if available” and its conditional preference are advisory and do not alone block a complete base ride. Other unsupported material semantics do block. Stops retain ordered source references and are PLANNED_PRODUCT_FEATURE, not permanently rejected product policy. Full stop booking support is a separate [future workstream](multi-stop-product-backlog.md).

Conditional destinations retain both alternatives; conflicting times retain both values without an effective selection; explicit destination corrections retain superseded provenance. Noisy route semantics stay SIMPLE, with fallback conditional on actual candidate/role failure. Review of identical pickup/drop text adds the existing grounded-endpoint check rather than assuming identical coordinates from text alone.
