# Search S2: bounded routing and extraction

Authoritative design: [Search S1](search-s1-architecture.md). This is a separate search workstream; responsibility Phase 8 remains incomplete and unchanged.

## Service boundary

`createRideSearchParser(provider, clock).parse(input)` accepts an immutable query identity (`id`, `revision`, `text`), explicit timezone, optional caller-supplied location candidates, and application-trusted explicit form context. It returns a provider-independent `BookingDraft`, structured issues, a route, fallback reasons, partial deterministic temporal resolution, and safe provider telemetry.

```text
query + trusted context
  -> bounded routing batch
  -> LOCATION_SEARCH: supplied candidate selection only
  -> BOOKING_REQUEST / SIMPLE: bounded extraction batch
  -> deterministic grounding, provenance and consistency validation
  -> BookingDraft + missing/ambiguous/policy/dependency issues
  -> or future-fallback-required
```

Complex requests stop after routing. An incomplete request is not made complex by application code. No field defaults are taken from booking creation. `SIMPLE_COMPLETE` describes extraction completeness; it is neither Places grounding, review readiness, user confirmation nor permission to create a booking.

No route, frontend control or production job invokes this service yet. There are no booking, fare, payment, assignment, Places, OpenAI/Luna, Terra, translation or responsibility imports/calls. Architecture tests traverse the local production dependency graph and guard composition roots.

## Contract and provenance

The strict Zod contract implements S1's field states and exact vehicle classes: `hatchback`, `sedan`, `suv`, `suv_premium`. A regression test compares them with the existing vehicle constants. There is no new booking-type enum.

- `UNSPECIFIED` means not supplied; explicit false remains a resolved false.
- `EXPLICIT_ANY` differs from unspecified. Exclusions are retained independently.
- Positive class strength is `REQUIRED` or `PREFERRED`; conflicting classes remain ambiguous.
- Locations contain candidate/selection references, never coordinates, place IDs or addresses generated by the model.
- Query spans use half-open UTF-16 offsets. Exact text, query ID/revision, candidate membership, unique IDs and surrogate boundaries are validated without repair.
- Resolved scalar components are tied to recognized source expressions; choosing a valid number/class alone is insufficient.
- `USER_FIELD` references are allowed only against application-trusted explicit form snapshots. New output must retain the same semantic field value and the exact snapshot revision. Incoming trusted snapshots may retain older owned `USER_FIELD` history, but reject future revisions and invalid query spans. An HTTP client body must never be promoted to trusted form context.

Context carry retains whole explicit fields when the new query leaves them unspecified. S3 still needs a granular follow-up merge for a new clock time plus an existing date, with component-level trust and provenance. It must retain the original relative-date anchor or a confirmed absolute calendar date. Old ungrounded location candidates and candidate-linked unsupported clauses cannot be attached to a new query revision; S3 must ground or preserve their original query lineage rather than rewrite spans.

S1 limits are enforced before spend: query 2,000 UTF-16 units, 24 location candidates, four ambiguity alternatives, eight date/time/passenger expression candidates, aggregate candidate text 8,000, serialized provider context 12,000, and 48 questions per batch. Candidate IDs cannot collide with selection sentinels. A limit failure does not amplify spend through fallback.

## Provider and request plan

The actual installed adapter is `@typesafe-ai/sdk@0.6.0`, `TypeSafeClient.systemOne`, using `choice` and `noul`. No free-text generation or score threshold is used. `createJevSearchProvider({client?, model?, clock?, timeoutMs?})` isolates SDK objects; default model is `jev-latest`, timeout 10 seconds, and SDK retries are explicitly zero. The SDK reads its normal `TYPESAFE_API_KEY` configuration; this implementation adds no credentials or live-test requirement.

Each question receives the original query/context and does not depend on another answer in the same batch. Routing always asks both query type and complexity independently. Extraction asks role selections/presence/consistency, timing and unsupported capability; vehicle, temporal/passenger candidate selection, flag and diagnostic questions are added only when relevant expressions exist.

Request counts: empty or invalid input **0**, unrelated/complex **1**, location search without candidates **1**, location search with candidates or simple booking **2 maximum**. Independent questions are batched; no hidden retries or model fallback occur.

Noul values remain unmodified diagnostics, not booleans. Operational presence decisions use categorical choices. Normalized choice confidence/distributions are retained for later evaluation. Metadata includes actual returned model, SDK version, attempted/completed requests, question counts, latency, and token counts when exposed. No monetary cost is fabricated.

## Extraction ownership

| Field | Ownership | Remaining dependency |
|---|---|---|
| Query type / complexity | Jev categorical routing + enum/combination validation | Live search benchmark in S5 |
| Pickup / drop / locationSearch | Jev selects supplied IDs; code validates membership, direction, overlap and consistency | Candidate generation and Places in S3 |
| Vehicle / strength / any / exclusions | Recognized source mentions + bounded choices + code guards | SUV-family exclusion scope; user selects an actual priced class later |
| Date | Code observes absolute/relative/weekday component expressions; Jev selects a bounded expression ID | Omitted-year and weekday product policy |
| Time | Code observes clock/daypart/precision components; Jev selects a bounded expression ID | Ambiguous period, daypart and approximation require clarification |
| Timing mode | Bounded choice + source consistency | No mention remains unspecified |
| Passengers | Numeric source candidates + bounded selection | Advisory only; booking enforcement unsupported |
| sharing / isOutstation / preferSafeRoute / needsCarrier | Recognized positive/negative spans + categorical decision | Absence is not a booking default |
| Unsupported clauses | Code preserves exact spans; bounded indicators can request review | Stops, return, rental, AC, conditional preference and other unsupported capabilities are not booking fields |

Scalar observation is conservative English lexical parsing; it does not generate location phrases or translate. Unrecognized or conflicting bounded extraction requires clarification/future fallback rather than invented values. Unsupported observations retain source-ordered supplied location candidate IDs when contained in their clauses. A provider-selected named unsupported type without matching observed evidence is rejected; a generic `OTHER` observation is explicitly review-required.

## Temporal resolution

The model never returns an authoritative ISO timestamp. Code resolves supported relative/calendar and exact clock components using the injected existing clock. Only the repository's established IST context (`Asia/Kolkata`/`Asia/Calcutta`) is resolved; other zones are policy issues.

Absolute dates require stated year/day/month and calendar round-trip validation. Bare/this/next weekdays and omitted years retain their expressions and `DATE_POLICY_CLARIFICATION_REQUIRED`. H12 hours require resolved AM/PM before resolution; H24 forbids it. Dayparts never become invented hours. Approximate clocks require confirmation. No timing mentioned never means immediate.

The exact existing WhatsApp backend scheduling function was extracted to `backend/lib/scheduling.js`; the old public wrapper delegates to it. Both parser and wrapper use **strictly more than 30 minutes** and **at most 168 continuous hours**. Existing WhatsApp behavior remains tested. Derived ISO output is outside BookingDraft.

## Failure and future fallback

Structured reasons distinguish provider timeout/error/invalid response/schema error, complex query, candidate dependency, role conflict, temporal conflict, extraction binding failure, unsupported requests and unresolved product policy. Provider errors are redacted, and failed extraction clears untrusted draft values. Missing fields alone request follow-up and do not invoke fallback. Product-policy gaps and unsupported enforcement do not become invented values.

Luna calls: **0**. S4 may consume the existing fallback route, original query, trusted partial values and issues. No automatic submission path exists.

## Legacy prototype and next phases

`backend/services/AI/bookingParser.ts` remains an existing legacy, unwired prototype, unchanged in S2. Production composition-root tests ensure it and the new service do not become competing wired parsers. Its nullable/incomplete-is-complex behavior must not be used as the search contract.

S3 owns production location candidate generation, Places grounding, active-field UX and follow-up integration. S4 owns the common-contract Luna fallback. S5 owns search-specific adversarial evaluation, necessary/unnecessary fallback calibration, model quality, latency/usage measurement and controlled rollout. S2 fake-provider tests verify contracts and safety, not live Jev extraction accuracy.

Unresolved product decisions remain: standalone location active-field policy, omitted year, bare/this/next weekday semantics, non-IST timezone policy, and generic SUV-family exclusion scope. Unsupported booking enforcement remains visible.

Responsibility Phase 8 is INCOMPLETE; it blocks responsibility Jev dual-shadow/auto-adjudication, and blocks neither Search S2 nor the next Search phase. No responsibility code or benchmark is changed.
