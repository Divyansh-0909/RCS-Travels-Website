# Search S3 — location grounding and follow-up validation

S1 and S2 remain the authoritative parser architecture and contract. S3 is a
search-only extension. Responsibility/Phase 8 implementation and configuration
are unchanged. S4 has not begun.

**Signoff status: COMPLETE.** Final source and individual survivor dispositions
are recorded in [the mutation signoff](search-s3-mutation-signoff.md) and
[its source-hashed audit](search-s3-mutation-audit.json).

## A. Architecture

```text
query identity + original text + explicit UI context
  → existing S2 Jev routing
  → conservative candidate generation for location/simple queries
  → existing bounded candidate-ID role selection
  → S2 provenance, membership, role/reversal checks
  → existing RCS Google proxy through PlaceSearchProvider
  → suggestions, including one match, require explicit selection
  → selected Place Details with matching authoritative ID/coordinates
  → immutable draft session + trusted selection registry
  → deterministic follow-ups + endpoint review
```

Complex, inconsistent and failed parser results do not enter Places grounding.
There is no semantic recovery, translation, Luna, Terra, booking creation, payment,
driver assignment or final-fare action in these modules.

## B–D. Candidates and role integrity

`locations/candidates.ts` produces exact UTF-16 spans; `end` is exclusive.
Methods are WHOLE_LOCATION_QUERY, DIRECTIONAL_CLAUSE, LABELLED_FIELD and
OVERLAPPING_ALTERNATIVE. LUNA_SOURCE_SPAN remains reserved in the shared contract
and is never generated by S3. Directional marker support is deterministic and
does not constitute translation.

IDs use SHA-256 over a JSON tuple of query ID, query revision, generator version,
span and method, with a `loc_` prefix and 24 hex characters. Query identity must
be revised when its text changes. Exact text is checked against the owning query;
old results cannot be applied to a later query revision.

Bounds reuse S2: 2,000 UTF-16 query units, 24 offered candidates and 8,000 aggregate
candidate text units. Individual candidates are bounded to 500 units. Overlap
limits and detector deduplication are validated alongside the final generator
campaign; exceeding a resource bound must not silently truncate a trip.

Jev selects offered IDs, never free-form geographic text. S2 continues to reject
unknown IDs, inconsistent roles, reversal risk and unexpected same-candidate
pickup/drop. Its categorical role-presence signal is kept separate from raw
noul diagnostics. Missing booking fields alone do not cause fallback.

## E–H. Places and standalone targeting

`PlaceSearchProvider` and `RcsPlacesTransport` isolate domain code from Google
payloads and UI SDK objects. The real HTTP adapter uses existing endpoints:

- `/api/googleAPI/autocomplete`
- `/api/googleAPI/details/:placeId`

The existing Google API-key configuration and India region restriction remain
in the proxy. Session requests forward one token from autocomplete to the
selected Details lookup and bypass legacy non-session caches. Details requests
include the authoritative ID field and verify it matches the selected ID.
This follows [Google's session-token flow](https://developers.google.com/maps/documentation/places/web-service/using-session-tokens).
Non-session response shapes and manual-form behavior remain compatible.

The exact candidate phrase is the autocomplete input. No Details request is made
for unselected suggestions. Safe telemetry counts total, autocomplete and details
requests; no pricing or monetary cost is invented.

Grounding states: NO_MATCH, USER_SELECTION_REQUIRED, RESOLVED and FAILED.
Every usable autocomplete result requires explicit selection, even a single
result. No-match and provider failures retain the original candidate and its
provenance. Infrastructure failures do not route to Luna.

Runtime validation rejects malformed matches, duplicate IDs, invalid coordinates,
stale revisions and unoffered selections. A Places details flow must return
GOOGLE_PLACES provenance. It cannot masquerade as a user map/current/saved choice.
Timeout handling covers both fetching and response-body decoding.

`TrustedLocation` stores selection ID, lat/lng, display text, confirmation time,
selection confirmation source and optional place ID. Google requires a nonempty
place ID. Explicit saved/current/map selections use the same RCS representation
and do not require another autocomplete request. Geography remains outside the
model-facing BookingDraft.

Standalone rules are frozen and implemented:

| Explicit context | Behavior |
| --- | --- |
| Active pickup | Ground for pickup |
| Active drop | Ground for drop |
| No active field | LOCATION_TARGET_REQUIRED; zero Places calls until choice |

An explicit target choice is retained as USER_FIELD/locationTarget provenance.
There is no default-to-destination behavior. Identical grounded endpoints produce
SAME_GROUNDED_ENDPOINTS and require clarification.

## I–M. Draft updates and follow-ups

`DraftSession` retains immutable parsed snapshots, original query identities,
trusted date anchors/timezones, an explicit user edit ledger and trusted location
selection registry. The current projection is replayed and validated against
that history. This is separate from S2's strict single-query input contract.
Historical query spans are never relabelled as a later query's spans.

Explicit form edits use USER_FIELD provenance and win over subsequent parser
revisions. Unspecified fields in a later parse preserve previous known values.
Accumulated booking intent survives standalone location follow-ups; each raw
query's classifier result remains unchanged in its snapshot.
Timing merges date and time independently. A date-only request followed by a time
selection preserves the original date source and the new time source. Relative
dates retain their original application-clock anchor; explicit relative-date
edits need an edit timestamp. Current scheduling bounds are rechecked using the
existing backend `parseScheduleTime` rule and controlled clock.

`LocationReview` maintains selected endpoints and selection history. Asynchronous
Details results must belong to the same query/candidate and current form revision.
An unchanged suggestion can be explicitly rebound after another field edit,
allowing two endpoint selections without another autocomplete call. Endpoint edit
revision stamps prevent rebinding an old standalone result after correction or
clearing. A query revision cannot be silently rebound.

Endpoint changes invalidate the actual fare, route, location-confirmation and
review-confirmation references. Time changes invalidate fare/route/review;
vehicle and other form edits invalidate fare/review while preserving unrelated
confirmed endpoints. Invalidations are consumed when those references are cleared.
No stale quote is submitted or recalculated as a final action.

Follow-up ordering is deterministic: conflicts, grounding, required fields,
temporal ambiguity, unsupported/policy issues, then review. Fields/codes break
ties and duplicates are removed. The UI can present only the first issue.
Known values remain in the draft; no restart is required. Obsolete role-specific
Places issues are dismissed after a trusted selection, while global provider
issues and unresolved-role errors remain visible. Policy warnings tied to carried
interpretation survive reparse and clear when that field is explicitly corrected.
Sourced ambiguity diagnostics also clear after explicit correction; unsupported
clauses remain preserved.

Unsupported stop/via, return, rental, AC/conditional-preference and advisory
passenger clauses remain preserved. No one-way trip is silently substituted.
Omitted-year, weekday, non-IST timezone and SUV-family semantics remain unresolved.

## N–U. Wiring and verification checkpoints

Customer-facing NL search is **NOT LIVE**. No frontend file is changed by S3.
Existing manual/autocomplete booking remains available. The additive internal
`backend/scripts/search-s3-review.ts` demonstrates query → suggestions → explicit
selection → draft/follow-up. It clearly labels its deterministic Jev/Places fakes;
it is not a provider preflight or real geography demonstration.

Focused tests include:

- Stable IDs, UTF-16/Unicode spans, ownership, multiword landmarks and bounds.
- A separate directional reversal cohort (X to Y, from/to, Y jaana hai X se,
  pick/drop, inverted drop/from). Fake-provider reversal checks are not live accuracy.
- All standalone active-field cases and explicit target-choice provenance.
- One/multiple/zero matches, details lookup, ID mapping, session lifecycle,
  timeout/body timeout, quota/config/provider errors and malformed provider output.
- Trusted saved/current/map choices, correction precedence, history tampering,
  immutable snapshots, date/time merging, scheduling and derived-state invalidation.
- No booking, model fallback, responsibility imports or geographic AI outputs.

Normal tests require neither live Jev nor live Google. Neither live preflight has
been performed. S5 will independently measure actual provider quality and latency.
