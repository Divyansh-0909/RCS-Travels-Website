# RCS compliance adversarial scenarios

These are audit/release scenarios, not new production tests. `FAIL (source)` means the traced path violates the stated invariant; `PASS (pure/mock)` applies only to the exercised arithmetic/fake transaction; `UNRESOLVED` means a business/legal/tax decision is required; `NOT EXECUTED` identifies a proposed integration/device/provider check. No real payment, driver record or deployed database was used. [Audit findings](rcs-policy-code-audit.md) and [fix plan](rcs-compliance-fix-plan.md) provide evidence, scope and approval boundaries. All P0/P1 findings have a scenario below.

## Scheduled advances, cancellation and provider operations

S-08 — ₹2,000 ride, historical ₹300 advance (RCS-07/17)

- When: rider confirms ₹100 cancellation and submits.
- Then expected behaviour: fee≤₹100; refund ₹200; driver compensation ₹100; RCS must not book entire ₹300 as revenue. Gateway fees/taxes remain separately unresolved.
- Current behaviour: pure charge function returns ₹100 and remaining ₹200. Cancellation transaction credits the fee and schedules the corresponding partial provider refund; request is not proof of processed refund.
- Pass/fail: PASS pure fee arithmetic; transaction/provider completion tested with fakes only. PDF full retention description FAIL.

Every money scenario proposed for implementation should check the invariant: captured customer money − successful refunds = satisfied fare/retained fee; each hold release goes to its owner; gross driver earning − commission − authorised recovery + reimbursements = net wallet/cash/payout view. Add transaction rollback/concurrent retry assertions and real PostgreSQL constraints in an isolated database. Provider retries, external channels and Android service behaviour need sandbox/device evidence. Historical bookings use original recorded payments, rate/decision versions and ledger entries unless an approved auditable correction explicitly changes them.
