# Phase 9D-1 operational and deployment gates

The executable worker is **offline and isolated**, not installed in the application job registry. The rehearsal SQL starts stopped. Its test clock is stored in shadow9d.control.now_at; production must use a reviewed server clock rather than applying this script. The script revokes PUBLIC defaults only in a harness-owned disposable database and is not a production migration.

Claim and completion both lock the control row. Stop commits a new epoch. A new claim while stopped returns no work; a model admission requires the lease/epoch and budget; a later commit must match the current epoch, owner, UUID capability, PROCESSING state and unexpired lease. An analyst already admitted by permit may begin/continue after a concurrent stop; the database check cannot atomically cancel a later external socket launch. New admissions are denied and late result commits are denied. Stronger transport-start/cancellation guarantees require the proposed independently controlled broker and are not implemented. Resume also advances the epoch, so an old response cannot become valid simply because the switch is on again. A commit that serialized before the stop is retained. The switch does not roll back that committed advisory or any business effect.

Two concurrent claims are bounded globally in the rehearsal DB, not separately per replica. Claims use durable status and SKIP LOCKED. Claims expire after two minutes; four attempts lead to manual review and retries wait at least 30 controlled seconds. This SQL prototype deliberately does not replace the existing Phase 7 backoff/manual retry policy; a deployment bridge needs a reviewed compatible contract. Queue admission is bounded at 100 pending/noncompleted records and request quota at 20 per rehearsal control budget. Existing duplicate identities suppress new work. Manual-review backlog occupies the queue budget, which intentionally applies backpressure but requires operator reconciliation. Duplicate result commits are rejected.

Stopping capture/evaluation does not stop the existing operational incident journal. The prototype does not wire an export/outbox into production collectors. Future capture must durably observe/export outside the customer/driver transaction so a broker/provider failure cannot block booking/cancellation/refund/recovery. Existing operational evidence collection has its own transaction/rollback behavior; no approved product atomicity is changed here.

A DB outage denies claim/admission/commit, preserves the last durable lease, and requires recovery after expiry. Audit writes and journal transitions share a transaction: inability to append aborts the transition. Failed direct SQL denials are recorded by the independent synthetic test supervisor; a malicious worker could omit its own application log. Deployed completeness therefore requires database/security-denial logs delivered by an independent custodian before activation. NOLOGIN blocks new connections, not existing sessions; commit stop first, revoke login and terminate worker-only connections using a separately controlled operator identity.

The network fence and environment allowlist prevent the actual test child from receiving live secrets or making normal non-loopback Node socket calls. They do **not** establish hostile-process isolation: the child shares a developer OS identity and repository filesystem. Do not infer that arbitrary child-process/native network calls, filesystem reads or reused Cloud IAM credentials are contained by that fence. The unapplied deployment proposal requires a dedicated image, filesystem, service account, DB login, private ingress and independently restricted egress/broker. No deployed grants/IAM were inspected or changed.

## Authentication and in-flight authority

The superseding session remediation is request-admission revocation for all 89 fully protected routes plus the conditional coupon route. Every protected human request requires a fresh matching active Clerk lookup. No cross-request positive cache, provider retry or offline fallback was added here. Admin role checks still consume cryptographically verified JWT role claims; the live session-status lookup does not refresh role metadata. Privileged role removal procedures need session revocation or separately reviewed current-role assurance. No role policy or middleware was altered. Admin evidence inspection, existing human review and any future human operational-control route must retain this shared guard plus role/object checks.

The measured prior sample median is about 354 ms and the caller deadline is 2.5 seconds. The installed SDK may continue its transport after the caller deadline; its slot stays outstanding, capped at 100 per process. Synthetic four-replica load executes the real guard with 8,000 independent lookups, 4,000 synthetic quota denials and stalled-slot/recovery assertions. It does not measure real provider capacity, production latency or actual incident volume.

Online offer polling is 2 seconds after response; tracking can poll every 5 seconds. The load model adds a declared 10-second location stress assumption, yielding about 712 lookups/s for 1,000 captains and 1,000 tracking customers before other Backend API traffic. Actual Android requested GPS intervals are 4 seconds active/20 seconds idle, with movement/heartbeat sending rules; OS callbacks and network duration are unmeasured, so the 10-second input must not be called a measured cadence. At one moving update per 4 seconds, the same demand assumption rises to roughly 862 lookups/s.

Clerk's general Backend API budgets are shared by application instance/secret key, not multiplied by Cloud Run replicas: [current documented limits](https://clerk.com/docs/guides/how-clerk-works/system-limits) are 1,000 requests/10 seconds for production and 100/10 seconds for development. Other user/session administration traffic consumes that budget. These hypothetical loads exceed the production default; replica scaling alone does not solve it. Production capacity agreement, faithful isolated HTTP journeys with latency/tail/outage distributions, shared budget monitoring and separately authorized production measurement remain activation gates. No live provider load or cache weakening occurred.

Admission does not cancel already admitted requests. Execution-time authorization assessment is required for payout batch iteration/external dispatch (driverPayouts.js), human review that can finalize a waiver, upheld finality that can hand off compensation/liability/strikes, appeal resolution, reliability-block removal, exceptional financial correction and operational resume/kill actions. Existing finality/consequence workers use their own durable authority, not a human JWT. A fresh human check immediately before irreversible dispatch could reduce a window but cannot atomically serialize Clerk revocation with an external payment. Any change requires explicit actor context, row locks/idempotency/provider-unknown-outcome verification and separately reviewed policy. No financial authorization or settlement was modified.

## Rollout sequence proposal

Approve privacy/projection/retention and calibration protocol; assign operational/security owners; build and verify a separate worker/broker deployment with independently denied app secrets/IAM/DB writers; install independent audit delivery and alerting; prove stop/recovery and provider budgets on a production-like isolated topology; review all gates and obtain separate explicit deployment/activation approval. Initial deployment must remain stopped and consequences off. Phase 9D-2, live calibration and production rollout have not begun.

SQL reference design follows PostgreSQL's [SECURITY DEFINER guidance](https://www.postgresql.org/docs/17/sql-createfunction.html) and [privilege ownership model](https://www.postgresql.org/docs/17/ddl-priv.html): separate nonlogin owners, no worker role membership, fixed trusted search_path with pg_temp last, and revoked default public EXECUTE. Supabase's [database-function guidance](https://supabase.com/docs/guides/database/functions) was also reviewed; its changelog markdown fetch was unavailable through the web tool. No Supabase-specific runtime feature or production setting was changed.
